# Behavioral Diff（/beh）

コードの変更と振る舞いの変化の対応（写像）を、正しく、抜け漏れなく、レビュワーの負担が少ない形で書き出す。

- 出力は、人間のレビュワーが変更を理解するためのもの。**あなたはレビュワーではない**。変更の良し悪し、バグの有無、テストの十分さ、意図に合っているかは判断しない
- 直接の影響だけでなく、コードの複雑さを通じて現れる、人が気づきにくい影響も含める。ただし、外から見える結果が変わらないもの（本質的に影響がないもの）は書かない
- 出力の形式は `references/output-template.md` に従う。まずそれを読む

## 引数

引数：`$ARGUMENTS`

次のどれかを受け取る。カレントディレクトリの git リポジトリが対象。

- `#123` または `123`：GitHub の PR か Issue の番号。番号だけでは区別できないので、`gh api repos/{owner}/{repo}/issues/123` を読み、`pull_request` の項目があれば PR、なければ Issue として扱う
- `a1b2c3d`（7〜40 桁の 16 進数）：コミットハッシュ
- `<始点>..<終点>`：コミットの範囲
- 引数なし：`HEAD` のコミット

`gh` が使えない、または GitHub のリポジトリでないときは、番号の指定はできないことを伝え、コミットハッシュでの指定を求める。

## 比べる範囲

- コミット：そのコミットの親 → そのコミット
- PR：base と head の分岐点（`git merge-base`）→ head。`gh pr view <番号> --json baseRefOid,headRefOid,body,commits,files` で取る。head のコミットが手元に無ければ `git fetch origin pull/<番号>/head` で取る
- Issue：次の 3 つを集める
  - その Issue を閉じた PR：`gh issue view <番号> --json closedByPullRequestsReferences`
  - 本文でその Issue を参照する PR（`Refs #<番号>` など。閉じた PR に出ないことがある）：`gh pr list --state all --search "<番号> in:body" --json number,body` のうち、本文が `#<番号>` に一致するもの
  - コミットメッセージでその Issue を参照するコミット：`git log --all -E --grep='#<番号>([^0-9]|$)'`
  - 集めた PR に含まれるコミット（`gh pr view <番号> --json commits`）と、その PR を取り込んだマージコミットは、コミットの側から除く
  - 対応する PR が 1 つで、残るコミットが無ければ、その PR として扱う
  - PR が無く、参照するコミットが 1 つなら、そのコミットとして扱う
  - 複数あるときは、古い順にコミット（または PR）ごとに出力する。飛び飛びのコミットを 1 つの差分にまとめない（途中の別の変更が混ざり、足し合わせても最終的な差と一致しない）。最初に、見つけたコミット・PR の一覧を示す
  - Issue の本文は「変更の目的」の出典として使う
- PR を取り込んだマージコミット：その PR として扱う
- コミットの範囲：指定された始点 → 終点

- PR は 2 点比較（`base..head`）にしない。base 側だけの変更が混ざる。分岐点からの差（`base...head`）を使う
- 「次のコミット」と言われたら、main の first-parent の履歴で次を取る。PR の内容をそのまま取り込んだだけのマージコミットは飛ばし、そう書き添える

## 手順

### S0 依存の自動更新か判定する
コミットや PR の作者、ブランチ名（`dependabot/…`、`renovate/…`）で判定する。該当すれば、テンプレートの「依存の自動更新」の形だけを出し、以降は行わない。

### S1 意図と変更点を集める
- 意図：コミットメッセージ、PR 本文、そこから参照されている Issue（`gh` が使えれば読む）。引用するので原文のまま控える
- 変更点：`git diff --stat` と差分。文書・テスト・コメントだけの変更を分けておく。ただし、**AI のコーディングエージェント向けの指示の文書**（`CLAUDE.md`、`AGENTS.md`、`GEMINI.md`、`.claude/`、`.cursor/rules` など、とそこから案内される文書）は外さない。エージェントの振る舞いを変える

### S2 局所的な変化を特定する
変更点ごとに、何が変わるか（値、分岐、例外、データの書き込み、外部への呼び出し、画面の状態、設定、エージェントへの指示）を特定する。変更していないコード（共通の関数、サーバの既存の処理）が結果を決めていることがあるので、差分の外も読む。

### S3 外側へたどる
変わったものを使う側へたどる。
- 呼び出し元
- データの読み手（テーブル → それを読む処理 → API → 画面）
- 設定・ルート・ミドルウェアなど呼び出し元を持たない変更は、その設定が効く全箇所
- エージェント向けの文書は、どの案内（`CLAUDE.md` の表、skill の description、hook など）から読まれるか
- 利用者には、配布済みの古い版のクライアントも含める（過去の版が使っていたかは履歴で調べる）

### S4 外から見える結果で止める
次のどれかに着いたら、そこを「影響が出る場所」とする。
- アプリ：画面の表示と操作、HTTP の応答（ステータス・ヘッダ・本文）、保存されるデータ、外部への送信
- 開発環境：テストの実行、ビルドの道具、リンタ・型の検査
- 作業者（AI）：エージェントが何をどう実行するか、どこで止まるか、何を確かめるか

処理全体の成否が変わるときは、その処理の結果を使う全項目が影響を受ける（API が 500 から 200 になれば、その応答の別の項目を出す画面も変わる）。

### S5 本質的かを判断する
外から見える結果が、実際に起こりうる条件で変わるものだけを残す。
- 結果が変わらない（途中で打ち消される、同じ値になる）なら書かない
- 条件が起こりえないなら書かない
- 外から見える結果に届く具体的な経路があって確かめられないもの（リポジトリの外の設定、ライブラリの中の変更）は「判断できなかったこと」に根拠つきで書く。根拠のない可能性は書かない
- 確かめられるなら確かめる（変更前後の関数を切り出して実行する、テストを読むなど）。どう確かめたかを書く

### S6 まとめる
同じ場所で同じように変わる条件を 1 つの項目にくくる。1 つの変更点から複数の影響、複数の変更点から 1 つの影響になってよい。出力の長さは、見つけた事実の数ではなく、振る舞いの変化の複雑さで決まる。

### S7 仕様と照らす
リポジトリの仕様の文書（例：`docs/spec/`、`docs/specs/`、`spec/` の文書、`SPEC.md`、`docs/requirements*`）を探す。振る舞いの変化（と、変更が記録・確認しているアプリの振る舞い）について、対応する記載があるか、変更後の振る舞いと一致するか、仕様の更新が必要か、この変更の中で更新されているかを書く。

### S8 読み違えやすい箇所に注意を書く
変更を読んだ人が、変更の意味や範囲を読み違えるおそれがある箇所を探す。変更した箇所と食い違う記載やコードが別の場所に残っている、似た状況なのに場所によって扱いが違う、2 つの条件を同時に満たす必要がある、のどれか。見つかれば、その振る舞いの変化の項目に「注意」として、何と何がどう違うかを両方の場所つきで書く。どちらが正しいかは書かない（書き方は `references/output-template.md`）。

## 出す前の点検

- [ ] 変更の目的を出典つきで引用したか（無ければ「目的の記載なし」）
- [ ] 振る舞いの変化を、コードの説明ではなく外から見える結果で書いたか。アプリ・開発環境・作業者（AI）のすべてを確かめたか
- [ ] 各項目に、レビュー対象のリポジトリの中の `ファイル:行` とメソッド名を書いたか。行番号は、変更後のコミットの内容で確かめたか
- [ ] 評価の語（良い・悪い、足りない、〜しかできない、問題ない）を書いていないか
- [ ] 表を使っていないか
- [ ] 中身の無い節に「なし」を並べていないか（「振る舞いの変化」以外は省く）
- [ ] 「判断できなかったこと」に、根拠のない可能性を入れていないか
- [ ] 出力の前後に、要約・前置き・感想・質問を付けていないか

## 出力

返答は、`references/output-template.md` の形で書いた出力だけにする。

- 出力の前後に、要約・前置き・感想・確認の質問を付けない
- レビュー対象のリポジトリの `CLAUDE.md` などに、報告の書き方の決まりがあっても、このスキルを使うときはこの形に従う
